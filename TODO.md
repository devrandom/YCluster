## Security

### [HIGH] Sandbox MinerU's outbound at the OS layer

Today the only SSRF mitigation on MinerU is its application-level
disable of `*-http-client` backends when bound to 0.0.0.0 (see
`mineru/cli/public_http_client_policy.py`). That blocks
attacker-supplied `server_url` / `backend: *-http-client` fields,
but does not stop a crafted PDF from triggering outbound fetches
via other parts of the pipeline (pypdf / pdfplumber resolving
external image URIs, font fetches, etc.).

We keep the 0.0.0.0 bind by convention (proxy reaches the backend
cluster-internal, low risk for inbound) but add a hard OS-level
outbound block on **both** deploy platforms.

**macOS (m\*)**: wrap `launchd` `ProgramArguments` with
`sandbox-exec -f sandbox.sb` and a Seatbelt profile that denies
all `network-out` except loopback.
- `config/ansible/macos/files/mineru/run-mineru.sh` — already
  binds `--host 0.0.0.0`, leave as-is.
- new `config/ansible/macos/files/mineru/sandbox.sb` — `(version
  1) (deny default) (allow network-bind (local ip "127.0.0.1:*"))
  (allow network-in (local ip "127.0.0.1:*")) (deny network-out)`
  plus the resource access rules MinerU needs (filesystem reads
  of model cache, HF home, etc.).
- `config/ansible/macos/setup-mineru.yml` — change
  `ProgramArguments` to `["/usr/bin/sandbox-exec", "-f",
  "/usr/local/etc/mineru.sb", "/Users/dev/mineru-venv/bin/mineru-api",
  ...]`, copy `sandbox.sb` to `/usr/local/etc/mineru.sb`.

**Linux/Nvidia (nv\*)**: add `--network=none` to
`mineru-podman.service`. The container has no netns interfaces
at all, so no `socket(AF_INET,...)` syscall can succeed. To keep
the API reachable, `mineru-api` binds to a Unix socket at
`/run/mineru/mineru.sock` (filesystem, not networking — works
under `--network=none`), and a sidecar `socat` process listens on
host TCP:8000 and bridges to the socket. Kernel-enforced, no
firewall rules need to be maintained.
- new `config/ansible/admin/files/mineru/run-mineru-uds.py` —
  monkey-patches `uvicorn.Config` / `uvicorn.run` to bind a Unix
  socket, then invokes `mineru.cli.fast_api.main()` unchanged.
- `config/ansible/admin/files/mineru/Containerfile` — change
  ENTRYPOINT to invoke the UDS wrapper.
- `config/ansible/admin/files/mineru/mineru-podman.service` — add
  `--network=none`, drop `-p 8000:8000`, add `-v
  /run/mineru:/run/mineru`.
- new
  `config/ansible/admin/files/mineru/mineru-podman-proxy.service`
  — runs `socat TCP-LISTEN:8000,reuseaddr,fork
  UNIX-CONNECT:/run/mineru/mineru.sock`,
  `After=mineru-podman.service`.
- `config/ansible/admin/install-mineru.yml` — install `socat` apt
  dep, install proxy unit, pre-create `/run/mineru/`.

- Per-node uplink failover watchdog (incident: `private/incidents.md`). A core node whose direct uplink's WAN is dead but whose next-hop is still ARP-reachable keeps its metric-100 DHCP default route and blackholes egress instead of falling back to the gateway VIP (`.254`, metric 500) — the kernel only drops a route on carrier/next-hop loss, not on dead-WAN-behind-a-live-router, so the leader can lose internet (and its rathole tunnel) while still looking up. Fix: a small per-node systemd-timer watchdog that probes the internet *forced through the own uplink* (reuse `gateway_health.py`'s `SO_BINDTODEVICE` probe so it still detects recovery after failover) and, with hysteresis, bumps the own-uplink default route's metric above the `.254` fallback when dead / restores metric 100 when healthy. Composes with the gateway VIP, which already lands on a healthy-uplink node (so the `.254` a demoted node leans on is guaranteed to NAT out a working uplink); the VIP holder's uplink is healthy by definition, so the same one rule needs no special-casing. **The bad route is DHCP-owned by systemd-networkd** (`proto dhcp`, metric 100, rendered from `netplan-cluster.yaml.j2`), and networkd re-asserts it on every lease renew (T1 ≈ 54min on a 2h lease), on any reconfigure, and on reboot — so a manual `ip route del`/metric change loses to networkd. The watchdog must therefore NOT fight networkd's main-table route; use one of: (a) a watchdog-OWNED lower-metric default via `.254` toggled on health (e.g. `metric 50` when the uplink is dead so it beats the DHCP `metric 100`, withdrawn when healthy — survives renews but not reboot); or (b) policy routing (`ip rule` selecting an uplink table vs a gateway table), independent of the networkd-managed route. Add a note to the cold-start runbook (`docs/operations/disaster-recovery.md`).

Options to investigate: (1) uplink-side VIP via keepalived on the 192.168.0.x segment — clean but only s2/s3 are on that subnet (s1 is on 192.168.9.x), so s1 can't participate and gateway-VIP leadership would need to be constrained to s2/s3; (2) static route `10.0.0.0/24 via <core node>` on the router so DNAT can target `10.0.0.254` directly — simplest but single-next-hop fragility; (3) a tiny UDP forwarder on each core node that knows which peer currently holds the gateway VIP and proxies wg packets there. Option 1 is probably the right call once s1's uplink is reconciled. Beyond follow-the-leader, the stronger goal is **redundant** inbound paths — multiple ingress IPs live at once (e.g. both core uplinks + the rathole endpoint), not just one address that moves on failover, so a single dead uplink/route doesn't strand remote peers (incident: `private/incidents.md`). WireGuard has **no native support** for this: a peer config carries a single `Endpoint`, with no endpoint list or failover (it's roaming-aware for the *client's* source address, and re-resolves a DNS-name Endpoint on `wg-quick up`, but never health-checks or fails over between ingress IPs on a live tunnel). So redundancy has to be built around wg: (a) low-TTL DNS for the Endpoint + client re-resolution (not automatic mid-tunnel); (b) a client-side watchdog that flips the peer endpoint (`wg set wg0 peer <pub> endpoint <alt>`) when `wg show latest-handshakes` goes stale — closest to true redundancy, and the smarts live on the remote nodes we control; (c) anycast / a front VIP / the UDP-forwarder above presenting one stable address over several paths. (b) composes well with the follow-the-leader work: the server side keeps moving wg0 with the VIP while clients independently pick whichever ingress is currently answering.
- `ycluster wg delete <hostname>` cascades into the node allocation, with no peer-only variant. `delete_peer` (`config/ansible/admin/files/ycluster/ycluster/utils/wg_config.py:183`) removes the wg peer *and* `/cluster/nodes/by-hostname/<h>` + `by-mac/<mac>` (symmetric with wg register, which created both), so once a node is re-bootstrapped onto the LAN, `wg delete` silently drops its live allocation — gone from the status page, loses its DHCP reservation (incident: `private/incidents.md`). Root cause underneath: a wg peer's AllowedIPs follows the node's allocation IP, so after a wg→LAN migration the peer carries a `10.0.0.x/32` that the gateway-VIP holder (the only node running wg0) installs as `10.0.0.x dev wg0`, black-holing the node's return traffic into the dead tunnel and making it unreachable from whichever node holds the VIP. Two fixes: (1) give the wg layer a peer-only removal (or have it refuse/auto-clean peers whose AllowedIPs fall in `10.0.0.0/24`); (2) make `dhcp delete` cascade to the wg peer so one command cleans a migrated node. Operational workaround is documented in `docs/operations/wireguard.md` (`wg revoke`, which keeps the allocation, + a manual `ip route del <ip> dev wg0` since `syncconf` leaves the wg-quick route behind).
- MiniMax-M3 reasoning parser: replace the always-think workaround with the proper prompt-check fix so M3 can reason *adaptively*. The shipped `minimax_m3` reasoning parser (`config/ansible/admin/files/minimax_m3_reasoning_parser.py`, loaded via `--reasoning-parser-plugin`) extracts `<mm:think>…</mm:think>` into `message.reasoning` correctly — but only when the prompt prefills the opener.
